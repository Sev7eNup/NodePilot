# CM1 smoke test after audit build (2026-10-09)

Installed build: `1.4.5-audit.20261009` on `HYD-CM1`, NodePilot service on HTTPS 8443.
The test was run against the installed service and SQL Server database `NodePilotFinal`.

## Result

- Service running; `/healthz/ready` returned HTTP 200. No Service Control Manager crash events in the checked post-update interval.
- The initial 45-minute cadence check had 38 passes, 6 failures and 7 skips. Four failures were cancellations around the deployment restart. The WMI test had already failed repeatedly before the deployment because its fixture queried `explorer.exe`, which does not run on this headless server. The new AI-agent case had not yet been installed.
- A fresh on-demand run of the existing suite had 36 passes, 2 failures and 13 skips. The failures were that same WMI fixture and the missing AI-agent case; all other enabled workflows passed, including the negative workflows with their exact expected failed step IDs.
- The WMI fixture now queries the always-present `services.exe`. The generator and emitted workflow were updated; the regenerated suite passed its five local coverage guard tests. A fresh CM1 WMI execution succeeded.
- The current 51-workflow, 398-case suite was installed on CM1. With integration and invasive opt-ins temporarily enabled, the full on-demand verifier had 40 passes, 1 failure and 10 skips. Live `llmQuery`, AI agents, service-management and scheduled-task tests passed. The one failure was the trigger driver: installing from a `localhost` base URL overwrote its webhook global with a loopback URL, which the hardened `RestApi:BlockPrivateNetworks` policy correctly rejected. Restoring the webhook URL to the configured allowed host `cm1.corp.contoso.com` and rerunning the trigger driver produced a successful execution (`7291d2be-af8d-4065-b588-310fd4c809b6`) with no failed steps.
- Trigger consumers were green in the cadence check. The negative remote-script-parity execution `fcacf921-32db-4c7c-b566-074d17a9ccba` failed by design at exactly the five manifest-declared steps; its checker and return step succeeded.
- Post-update CMTrace error-level log entries in the checked interval were only seven deliberate `[TestSuite] log` error messages. The support log had no error/fatal lines in that interval. No test service or scheduled-task fixture remained.

## Restored state and limits

The temporarily enabled `llmQuery`, AI-agent, service-management and scheduled-task workflows were disabled again. Their two temporary opt-in globals were removed. The suite has 51 definitions, 44 enabled, matching the pre-test enabled count. The webhook global now uses the configured CM1 hostname.

The named-SQL and email cases remained disabled for missing prerequisites. The service stop/start/restart cycle remained disabled because no disposable, startable target service was nominated; the suite deliberately does not pick an operational service. Some test-sandbox directories still contain `suite.db` files even though their SQL workflows succeeded; the suite janitor is designed to evict stale directories after one hour. The residue pattern occurred both before and after the deployment and is a test-cleanup issue, not evidence of an engine regression.
